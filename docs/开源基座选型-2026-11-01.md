# 开源安卓输入法基座选型（Agent 输入法）

日期：2026-11-01
调研方式：GitHub 元数据 + 各仓库源码/CI 配置实读（源码已下载到 `C:\Users\A'maris\Documents\ChatGPT\agent输入法\base-test\`）+ 本机工具链 `sdkmanager --list` 实测。README 宣传语一律不作为结论依据，表中结论均附可核对的文件或字段。

## 结论（TL;DR）

**基座选 HeliBoard（`HeliBorg/HeliBoard`，GPL-3.0，版本 4.3-beta1）。** 把我们已跑通的 librime 中文栈（`librime.so` + `rime_jni.c` + `assets/rime` + `ChineseInputEngine.kt` + `t9_syllables.h`）整体移植进去，Agent 面板按 HeliBoard 现有的 InputView / 功能键 / Compose 体系实现。换基座的理由是"壳的稳定性"：旧项目崩掉的功能（insets、候选栏不显示组合串、敏感域误判导致无候选）几乎全在壳层，而壳层正是成熟基座已经验证过的部分。

- 备选（中文优先、愿意付工具链代价）：**Trime（同文输入法）**。补充实测（2026-11-01）：Trime 在本机也**已构建成功**（`BUILD SUCCESSFUL in 4m 14s`，`com.osfans.trime-7c55dd1-x86_64-debug.apk` 16,510,415 B），代价是便携 git + `python3` 别名 + 三个插件目录手动拷贝（无 Developer Mode 时的软链接替代），详见第六节。
- 排除：**fcitx5-android**（需要 MSYS2 + extra-cmake-modules + gettext，约 20 个 submodule，且键盘布局不可自定义，九键要动核心代码）；**FlorisBoard**（无中文拼音方案，仅 Apache-2.0 许可占优）。

## 一、为什么不再扩写自研壳

`docs/Release-内测候选版-验收-2026-10-31.md` 的"已知问题与风险"里，除词库质量外全部是壳层问题：

| 故障 | 性质 | 成熟基座是否已解决 |
| --- | --- | --- |
| `TYPE_TEXT_FLAG_NO_SUGGESTIONS` 被判敏感 → 系统搜索框/Wi-Fi SSID 框无候选、不能打中文 | 自研壳的 inputType 判定 | 是（按 inputType 分支是 AOSP 原生逻辑） |
| Agent 草稿输入拼音时草稿框不显示组合串 | 自研壳的 composition 显示 | 是（LatinIME 的 composing 渲染是原生的） |
| 敏感态点「九键」无提示不切换 | 自研壳的键盘切换 | 是（基座用 KeyboardSwitcher 统一管理） |
| 首帧 insets 把第 4 排画到导航栏下 | 自研壳的 inset 计算 | 是（基座有完整 insets/尺寸处理） |

结论：继续在自研壳上补这些，是在重复解决 AOSP 十年前就解决的问题。**基座价值 = 免掉壳层维护成本，把工时全部投到 Agent 层。**

## 四、做 Agent 功能要动的扩展点（源码级）

**HeliBoard（选定）** —— 以下行号均为 4.3-beta1 源码实读，不是推测：

- **按键拦截点（决定性的那个）**：`latin/KeyboardActionListenerImpl.kt:106` 的 `override fun onCodeInput(primaryCode, x, y, isKeyRepeat)`，它在 `:96` 调 `inputLogic.onCodeInput(...)`。中文模式在这里**提前分流并 return**，即可完全绕开 AOSP 的 `InputLogic`/`WordComposer`/词典建议管线——不需要"在 Latin 管线内部造中文模式"。

## 五、为什么是 HeliBoard

1. **唯一在本机能"零额外系统依赖"构建的候选**（JDK17 正好、无 submodule、无 MSYS2、无 git）。Trime 与 fcitx5 都要先补一套本机没有的构建环境。
2. **壳最稳、最没有历史包袱**：AOSP LatinIME 血统 + OpenBoard 分支，6.4k★、日更；键盘尺寸/insets/候选栏/composition 都是原生实现，正是旧壳翻车的地方。
3. **中文不需要重造，只需要搬运**：我们把已经验证过的 librime 栈原样搬进去——`app/src/main/jniLibs/{arm64-v8a,x86_64}/librime.so`、`app/src/main/cpp/rime_jni.c`、`app/src/main/assets/rime/`、`ChineseInputEngine.kt`、`cpp/t9_syllables.h`。九键 = 一份自定义 `layouts/main/*.json` + 现有 T9 换码表。
4. **改造成本最低**：加 Agent 键只写一个 JSON 条目 + 一个 KeyCode 分支；面板用已启用的 Compose；上下文/写入靠成熟的 `RichInputConnection`。

**代价（必须承认）**：HeliBoard 自带中文为零，中文输入法体验的上限取决于我们移植的 librime 方案与词库（当前是 `luna_pinyin` 全拼 + `essay`，够用但不如商业词库）；九宫格要自己定义布局。Trime 则相反——中文/主题开箱即用，但构建门槛和"往主题驱动的 UI 里塞 Agent 面板"的改造成本更高。

### 对"应该选 Trime"这一异议的回应

独立调研位（`ime-survey`）的推荐是 **Trime 优先、fcitx5 次之、HeliBoard 最后**，核心论据两条，逐条核对后都不成立或已被我们自己的资产抵消：

1. "HeliBoard 没有 CJK 输入通路，候选栏是 AOSP 单词建议模型，接 librime 等于在它内部重建中文管线，正是你们自研壳失败的那部分工作。"
   —— 半对半错。半对：HeliBoard 的默认管线确实是 `WordComposer`→`BinaryDictionary`。半错在"重建"：`KeyboardActionListenerImpl.kt:106` 是单一入口，中文模式在那里分流 return 就绕开了整条 Latin 管线；`RichInputConnection.setComposingText/commitText` 是现成的；候选只要包成 `SuggestedWords`（公开构造）就进候选栏。**中文预编辑、候选提交这些正是我们旧项目已经写完的代码**（`ChineseInputEngine.kt` 可零修改搬入），不是要从零写。
2. "librime .so 仍要自己编，native 负担并不更轻。"
   —— 不成立。`project/app/src/main/jniLibs/{arm64-v8a,x86_64}/librime.so`（2.6 MB 等一套 so）**已经编好并在模拟器上验证过**（`librime initialize=true version=1.17.0`）；而 Trime 是 10 个 native submodule 现场编 librime（且它把三个插件用 `file(CREATE_LINK ... SYMBOLIC)` 软链进 `librime/plugins/`，Windows 无 Developer Mode 时必须手动改拷贝——详见第六节实测）。<br>**更正（2026-11-01 实测）**：此前"没 git 就直接过不去"不准确——`ProjectExtensions.kt:13` 的 `runCmd` 用 `setIgnoreExitValue(true)`，`git describe` 失败只回退默认版本串、不中断构建；真正需要 git 的是 submodule 拉取，而 MinGit 便携版已验证可解决。

异议里最有价值的一条是对的：**"若目标是尽快拿到一个能日常打字的键盘，Trime 补九键主题 YAML 比 HeliBoard 造中文模式少"**。所以判断标准取决于目标：以"中文打字体验"为目标 → Trime；以"Agent 功能闭环 + 基座可维护"为目标 → HeliBoard。本项目目标是后者，且中文引擎已自有，故仍选 HeliBoard。若你更看重中文开箱即用，改走 Trime 只是换目录、不浪费本报告的任何结论。

## 六、Trime 构建验证（2026-11-01 实测通过）

**结论：Trime 在本机能构建，而且构建链比预想干净——`BUILD SUCCESSFUL in 4m 14s`，产物 `com.osfans.trime-7c55dd1-x86_64-debug.apk`（16,510,415 B）。**

| 项 | 实际情况 |
|---|---|
| 源码 | `git clone --depth 1 --branch develop --recurse-submodules --shallow-submodules https://github.com/osfans/trime.git C:\trimebuild\trime`，约 2 分钟；10 个一级 submodule + librime 的 6 个 deps + snappy 的 2 个三级 submodule 全部到位（files=4427 / 86 MB） |
| git | 本机原本没有。用 portable **MinGit 2.56.0.4** 解压到 `E:\AgentImeTest\git\cmd\cmd\git.exe`，只需把它加入 PATH；**无需安装、无需管理员** |
| JDK | 本机 **JDK 17** 就能构建（上游 CI 用 25，不是硬要求） |
| NDK / CMake | 不装上游的 NDK 30 + CMake 4.1.2；用 `NDK_VERSION=27.0.12077973`、`CMAKE_VERSION=3.31.6` 环境变量覆盖即可（`ProjectExtensions.kt:36-44` 支持 env 覆盖），**不需要改一行源码** |
| Python | `OpenCCDataPlugin` 会 spawn `python3`；把 python 目录内的 `python.exe` 复制一份 `python3.exe` 并放 PATH 即可（用 3.12.14） |
| ABI | 设 `BUILD_ABI=x86_64` 只编一个 ABI 省时；真机需改 `arm64-v8a` |
| 构建脚本 | `C:\trimebuild\build-trime.ps1`（加载 `E:\AgentImeTest\env.ps1`、设 PATH/代理/版本变量、`gradlew assembleDebug`、日志 `C:\trimebuild\build.log`） |

**唯一真正踩到的坑（Windows 特有，必须记录）**：`app/src/main/jni/cmake/Rime.cmake:9-14` 用 `file(CREATE_LINK "${CMAKE_SOURCE_DIR}/${plugin}" "${CMAKE_SOURCE_DIR}/librime/plugins/${plugin}" COPY_ON_ERROR SYMBOLIC)` 把 `jni/librime-lua|octagram|predict` 软链接进 `librime/plugins/`。本机无 Developer Mode，`mklink /D` 实测报 `You do not have sufficient privilege to perform this operation.`，CMake 只留下空目录，于是 configure 阶段报：

```
CMake Error at librime/plugins/CMakeLists.txt:47 (add_subdirectory):
  The source directory .../librime/plugins/librime-lua does not contain a CMakeLists.txt file.
```

解法：先删掉三个空目录，再用 `robocopy /E` 把 `jni/librime-lua`、`jni/librime-octagram`、`jni/librime-predict` 真实源码拷进 `librime/plugins/<同名>`，并把 `jni/librime-lua-deps` 拷成 `librime/plugins/librime-lua/thirdparty`（该插件要 `thirdparty/lua5.4/lua.h`）。拷完重跑即通过；native 编译（librime + lua + octagram + predict + snappy + leveldb + opencc + marisa + yaml-cpp）约 3 分钟。

**这次验证对选型结论的影响**：Trime 不再是"构建门槛高到不可行"，而是"Windows 上多一步符号链接替代 + 便携 git + python3 别名"。它中文/词库/主题开箱即用、九宫格仍要自写主题 YAML（默认主题与 `tongwenfeng.trime.yaml` 都只有 26 键布局，全仓 assets 里 grep `t9|nine|九宫` 零命中）。也就是说两条路的真实差距回到"中文引擎谁来搬"：选 HeliBoard = 搬我们已有的 librime 栈；选 Trime = 搬 Agent 面板进它的主题 UI 并补九键主题。
